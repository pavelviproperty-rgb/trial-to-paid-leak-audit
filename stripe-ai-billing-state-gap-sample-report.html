Executive diagnosis

The core problem is not that Stripe failed to bill. The main leak is that product access and quota enforcement continue after Stripe moves certain accounts into states that should reduce or block usage. Credits, retries, and restore-access logic are being decided in separate places with no shared row-level truth.

Facts used

  • Stripe product, price, and meter screenshots.
  • 3 redacted customer lifecycle examples.
  • Current quota and entitlement rules.
  • One internal usage ledger export and webhook event list.

Unknowns

  • Whether all delayed access revocations are intentional grace periods.
  • Whether credits are versioned consistently across old plans.
  • Whether certain retry paths should restore access automatically.

Top 3 state gaps

  • Quota drift: paid usage rows exist after plan limit should have blocked the workflow.
  • Restore-access drift: invoice is paid after retry, but entitlement stays stale until manual support touch.
  • Credit versioning drift: older accounts keep legacy credit assumptions after plan migration.

Fast fixes first

  • Log one row per customer lifecycle with billing state, usage state, and product-access state.
  • Define which states hard-stop usage immediately and which get a timed grace window.
  • Separate restore-access logic from generic invoice-paid handling.

Instrumentation to add

  • billing_state, usage_state, and access_state on one row.
  • Plan version and entitlement version for every paid workflow.
  • Retry outcome and restore-access lag in minutes.
